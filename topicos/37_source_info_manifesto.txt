DECISOES DE DESIGN (travadas com o usuario 2026-08-29)
====================================================================

1. HELLO nao muda. A informacao vai na MANIFEST_DATA (CONTROL 0x0004), que
   ja "descreve o source" e ja tem manifest_format_version para crescer.
   Ver topico 36 -- o caminho prime->cache->serve->parse ja funciona.

2. O BTP nao tem codigo de manifesto: e spec (docs/) + vetores. A lib C++
   (codec/fragmentation/stream/aead) para no frame. O layout da MANIFEST_DATA
   vive so em docs/commands.md secao 3 e e implementado a mao em 3 lugares:
     - bally_OS  lib/ManifestResponder/ManifestResponder.cpp  (escreve)
     - bally_dongle lib/ManifestCache/ManifestCache.cpp        (guarda/serve)
     - TraceView lib/protocol/manifestclient.cpp               (le)
   Entao "implementar no BTP" = editar docs + adicionar 1 vetor + bump 2.1.0.
   NENHUM .cpp/.hpp da lib BTP e tocado.

3. Formato da entrada: LABEL NA WIRE, SEM REGISTRO.
     info_entry = { key:utf8_u16, label:utf8_u16, value:utf8_u16 }
   - key    = identificador estavel de maquina  ("fw_version")
   - label  = nome legivel para exibir           ("Firmware"); pode ser vazio
   - value  = o dado, sempre texto               ("2.1.0-rc1", "2", "16777216")
   O BTP define so a mecanica (info_count + formato da entrada) e uma lista
   de key RECOMENDADOS (nao obrigatorios, nao exaustivos). Consumidor que
   nao conhece a key exibe label/value mesmo assim.

4. config_revision NAO cobre source_info. config_revision continua sendo
   "o catalogo de topicos/acoes mudou". Uma resposta NOT_MODIFIED ainda
   carrega o source_info fresco (ele e informativo, nao e descriptor).
   Isso evita que editar o friendly_name invalide o cache do catalogo, e
   resolve a tensao ja documentada em bally_OS RobotSettings.h:180.

5. Valores sempre utf8_u16 (string). Sem value_type tipado.

6. Opcionalidade em 3 camadas:
   (a) manifest_format_version = 1 -> sem bloco (comportamento atual).
       = 2 -> tem o bloco source_info logo apos source_name.
   (b) info_count pode ser 0 -> source em formato 2 que nao quer publicar
       nada manda lista vazia. Valido.
   (c) por entrada -> o responder inclui so as key que ele tem. Nada e
       obrigatorio. Ordem nao importa.

7. FICA DE FORA de proposito: senha OTA (nunca num anuncio de descoberta;
   endpoint sim, segredo nao), qualquer coisa que muda a cada segundo
   (uptime, heap -- isso e STATUS).


====================================================================
LAYOUT NA WIRE (MANIFEST_DATA, manifest_format_version = 2)
====================================================================

  offset 0..57   identico ao formato 1
  offset 58      source_name              utf8_u16
  --- novo, so em formato 2 ---
  var            info_count               uint16_le
  var            entries    info_count x  { key:utf8_u16, label:utf8_u16, value:utf8_u16 }
  --- fim ---
  var            topic records            (topic_count deles)
  var            action records           (action_count deles)

Formato 1: sem info_count, payload termina apos os records (como hoje).
Um parser so-formato-1 REJEITA um payload formato 2 (ja faz: formatVersion != 1).
Um parser formato-2 aceita os dois (formato 1 -> info_count tratado como 0).
Deploy move as duas pontas juntas (nao ha negociacao no MANIFEST_REQUEST).

key RECOMENDADOS (quando o source tem o dado):
  name           nome humano configurado
  description    texto livre
  model          modelo de hardware
  fw_version     string de versao de firmware
  fw_build       timestamp de build
  chip           modelo do chip
  chip_revision  revisao de silicio
  ota_partition  particao de firmware rodando
  ota_endpoint   onde um update e servido (NUNCA um segredo)

Limites novos (commands.md secao 6):
  Source info entries              32
  Source info key                  64 octetos
  Source info label ou value      256 octetos
